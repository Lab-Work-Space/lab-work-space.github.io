A staged workflow for Claude Code agents

Claude Code can run subagents, and a long session with several of them tends to drift. The goal gets reinterpreted along the way, work is called done without anyone reviewing it, and a closed laptop means starting again from the conversation. This guide describes a workflow that addresses those three problems with plain files and fixed stages, and shows how to try it with a free kit.

What is in which edition. The free Crewlatch lite edition has one skill and four agents, and runs five stages with a checkpoint after each. The full edition has twelve agents and adds two security gates, a retro, and classification of the request. Whatever is marked (full edition) below is not in the lite edition.

The problems

  • The thread is lost. Context grows, and the early decisions, such as what was agreed and what was ruled out, are the first to be forgotten or restated differently.
  • Work is declared done unreviewed. The agent that wrote the code is the one that says it works. Nobody checks the spec before code exists, or the code before it ships.
  • Interrupted work cannot be resumed. Without a record outside the conversation, a crash, a closed terminal or a new day starts from nothing.

The idea

The workflow is a process that the main Claude Code session follows. It is written down once, in a skill, so it does not depend on remembering it each time:

  • A request is classified (full edition). A bug fix, a documentation change and a new feature need different stages, and the session says which stages it will run before it starts. In the lite edition the session names the stages it will run from a fixed list of five, and skips the ones the task does not need.
  • Work goes through named stages. Agree the goal, plan, build, test, document. Each stage has an owner, an agent with a written scope, and each is dispatched with a brief that carries paths and facts, not the conversation.
  • Each stage ends in a checkpoint. A file records what is done, what is pending and what waits for you. The next stage starts from the file.
  • Two gates review before the point of no return (full edition). One reviews the spec for security problems before any code exists. The other audits the code before release.
  • A retro proposes rules (full edition). At the end, lessons become proposed rules, and you approve, edit or reject each one.
  • You stay in the loop. The main session asks you questions, one at a time, and stops for your approval at the spec.

The agents do not talk to you and do not dispatch each other. Only the main session does both, and that keeps one place where decisions are recorded.

What a checkpoint holds

A checkpoint is a Markdown file for one project, written after each stage. This is an example of one, shortened, in the layout of the template that the kit installs:

---
project: "health-endpoint"
updated: 2026-01-15T10:30
status: "waiting_user"
---

# Checkpoint: health-endpoint

## Request
Add a /health endpoint that returns the build version.

## Stages
| # | Stage | Status | Owner | Output |
| :--- | :--- | :--- | :--- | :--- |
| 0 | Context | done | main | none |
| 1 | Agree the goal | done | main | spec approved |
| 2 | Plan | done | pm | docs/plans/health.md |
| 3 | Build | in progress | backend | TASK-001 |

## Waiting on user
- none

## Next action
Dispatch the tester with the original request.

The values above are an invented example. In use the file lives at ~/.claude/team/state/<project>.md. When the skill runs again and finds a checkpoint whose status is not done, it asks you whether to resume or start the new request, and never resumes silently.

Try it with the lite edition

Crewlatch lite is the free kit that implements the stages and checkpoints: one skill, team-dev, four agents (pm, backend, tester and document), five templates and a token policy. It needs Claude Code and bash, and downloads nothing. It is tested on macOS.

Download the zip from the releases page of the crewlatch-lite repository on GitHub, unzip it, go into the folder and look before you install:

./install.sh --dry-run   # see what would change
./install.sh             # install into ~/.claude

If files with the same names exist, the installer stops and changes nothing. Then start a Claude Code session in a project folder and type:

Use the team-dev skill. Add a /health endpoint that returns the build version.

Claude says which stages it will run, asks its questions one at a time, and writes a checkpoint after each stage. To continue later, type Use the team-dev skill. Resume. To remove the kit, run ./uninstall.sh from the folder you installed from; your checkpoints are kept.

Nothing here is a measured result. The kit describes a mechanism, and whether it suits your work is for you to find out on a real task. It uses more tokens than a single session, because several agents each read context and do their own work. For a one-line fix, skip it.

What the lite edition leaves out

The lite edition has no security gates, no classification of the request and no retro. The full edition adds them, with eight more agents (sa, security, frontend, database, ai-prompt, devops, git and optimizer) and a guide with a worked example. It costs 29 USD: Crewlatch on Gumroad.
